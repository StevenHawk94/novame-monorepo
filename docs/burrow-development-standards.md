# Burrow 开发基线与变更验收规范

版本：1.12 · 更新日期：2026-10-26 · 适用：Mobile、API、Admin、数据库、素材与测试。

本文用于新增功能、UI 调整、修复 Bug、依赖升级和发布时共同遵守。它是当前 Burrow 的开发约定，不是旧版 NovaMe 产品说明，也不代表每项目标都已在所有设备上验证通过。

约定的优先级：用户明确批准的新需求 → 本文当前产品不变量 → 对应领域实现与合同测试 → 历史说明。发现冲突时先指出冲突，不得自行改变业务规则来让实现或测试通过。

标记说明：

- **必须**：不能在普通改动中破坏；改变它需要明确批准、迁移方案和配套测试。
- **验收目标**：本规范设定的工程门槛，不等于当前全设备实测结果；不达标必须记录原因、影响和处置。
- **现状记录**：有时间、范围和证据限制的结果，不是永久保证。

### 业务约定变更与文档同步规则

- **未经用户明确确认和许可，不得更改本文既有的业务逻辑、基础约定或验收标准，也不得先改实现再修改文档使其看似合规。** 新增功能、修 Bug、性能优化或笼统的“继续执行”不自动授权改变未明确讨论的既有约定；有冲突或授权范围不清时，先说明原规则、拟改规则及影响，等待确认。
- 用户明确批准某项调整后，仅在批准范围内实施；其他未涉及的约定继续有效。确认业务调整不自动授权生产迁移、部署、发布公告、启用强更或发布 App。
- 完成任务时，必须同步修订本文受影响的原章节、数值、流程、检查清单及对应测试/兼容说明，不能只在末尾追加一条新规则，却保留正文里相互矛盾的旧规则。未实施或未验证的部分明确标为待完成，不写成已生效。
- 每次经批准的约定调整都更新文档版本与日期，并在下方变更记录中注明确认依据、原规则 → 新规则、涉及章节和验证/上线状态。确认依据使用可定位的任务/消息引用或用户确认内容摘要，不推断不存在的授权。
- 最终交付必须提供更新后本文的链接，并简述本轮修订内容及尚未生效的客户端/服务端范围；无需用户再次提醒才同步文档。未获批准的建议只作为待确认事项说明，不替换现行基线。

## 1. 先记住这 12 条

1. 客户端正常操作不能等待服务器往返才给反馈；也不能伪造已经获得服务端确认的事实。
2. 先可靠保存本地意图，再乐观反馈；保存失败不能假装已发送或已受理。
3. 服务端决定权限、余额、价格、配额、最终结果和账本；本地余额与完成状态用于即时判断和展示。
4. 超时不等于失败。重试同一个意图必须使用同一个幂等键和原始请求，不能再次扣款或发奖。
5. 已提交成功的回执，不能被 React、动画、评分、缓存或监听器异常改写成“购买失败”。
6. 红点不是“收到数据事件”的同义词：只有当前身份、当前内容版本及打开所需内容均就绪，才能发布可操作提醒。
7. 看到红点后，正常路径应直接从准备好的数据打开；不能点击后才开始取核心内容、下载必需素材。
8. A、B 各自拥有房间、库存和钱包；配对不意味着共用装修或互相拥有商品。
9. 同一业务的不同入口共用控制器和服务端结算路径，不允许各写一套购买、扣款、发奖或照片逻辑。
10. 功能只订阅自己需要的字段，通过约定接口交互；不能因为钱包、计时器或通知变化重绘整棵 App。
11. 原生渲染器、图片解码器、视图回收池、全局监听器也是共享资源；JS 组件拆开不等于已经隔离。
12. 修复完成必须有反例测试、跨功能回归与发布证据。禁止仅凭“这次点开了”宣称全场景稳定或零掉帧。

## 2. 流畅度：明确区分帧时间、点击反馈和页面进入时间

### 2.1 “50ms 以内”应如何理解

单帧 50ms 对应约 20fps，不能作为常态流畅标准。60fps 的单帧预算约 16.7ms；30–50fps 对应约 33.3–20ms。用户此前接受的参考是 30–50fps、实际操作不出现明显卡顿，而不是所有设备严格复制某一次采样。

本规范把 **50ms 用作点击即时反馈目标和慢帧警戒线**，不把它当作每帧可以消耗的常规预算。以下是本规范的验收目标，不是已有测量的重新命名：

| 指标 | 目标与判断方式 |
| --- | --- |
| 按下、选中、禁用防重等即时视觉反馈 | 正常负载目标 ≤50ms；不等待网络 |
| 常态动画帧预算 | 按设备刷新率规划；60Hz 场景以约 16.7ms 为预算 |
| 单帧 >50ms | 记录为慢帧，定位发生阶段；连续出现或肉眼停顿必须处理 |
| JS 同步工作 | 优先拆成约 4–8ms 的可让出片段；不得把 50ms 长任务当成正常开销 |
| 已准备页面的导航派发 → focus 回调 | P95 目标 ≤150ms；它不等于实际首像素或完整可交互时间 |
| 已准备页面的首个可用内容 | P95 目标 ≤250ms；核心内容不依赖点击后的网络请求 |
| 返回页面 | 优先显示保留的完整页面，不重新盖 Splash，不闪空白后重建 |
| 后台信息到达 | 不夺走当前焦点、不重复导航、不弹多层弹窗、不阻塞当前手势 |

超过目标不能改测试阈值后直接算通过。必须区分产品代码回退、设备能力、构建模式和环境噪声；有明确影响的例外需要单独记录和批准。

### 2.2 必须保留的实现方式

- 可点击区先响应，再调度非必要工作。网络、持久化清理、大数组整理和大图解码不能塞进点击回调的同步主链。
- 使用领域 selector、结构共享和稳定引用。无关字段变化不应制造新的页面快照。
- 隐藏页面停止非必要重绘、定时器和预热；重新获得焦点时读取最新准备快照。必要的后台服务如音乐、上传队列不能简单随页面隐藏而停止。
- 钱包、红点、计时器分别在小范围订阅。Affection、Adventure、Plushie 展示不应额外订阅无关钱包变化。
- 后台快照整理允许分片让出 UI，但最终发布、账号撤销和本地意图投影必须保持一致。身份失效不能为了“流畅”延迟清理。
- 列表分页、首屏分批渲染；预热可见范围和下一步必需内容，不预热整套商品/历史/所有页面。
- 相同身份、业务版本、商品目录和会员状态下复用准备结果；不能每次 focus 都 force 全量请求。
- 不通过后台挂载多个真实页面来“预热”，这会同时引入监听器、计时器和原生视图副作用。
- 动画使用原生驱动/工作线程能力；业务完成必须由单一状态机控制，不能让多个动画回调重复发送。

### 2.3 性能验收方法

至少分别记录冷启动、首次打开、准备后重复打开、连续返回/切 Tab、后台数据更新到达、前后台恢复。主要入口重复约 20 次；如果样本少，必须标注样本数，不能把少量样本的 P95 当成稳定结论。

使用 Release 或 production/minified JS + Hermes 的原生环境复核；Expo/Metro 的开发额外开销不能直接代表正式版。不得同时编译、大批量跑测试并进行正式性能采样。

记录设备、系统、构建、刷新率、场景、P50/P95、慢帧数量/比例、最大卡顿、运行错误及首屏截图。UI/JS/导航回调指标分别记录。平均 FPS 合格不能掩盖一次明显冻结。

视频只能辅助判断视觉连续性；编码为 25fps 的视频不能证明 App 只跑 25fps，也不能证明 App 跑到了 50fps。

## 3. 用户端即时反馈与服务端静默处理

### 3.1 一次操作至少区分五种事实

| 状态 | 含义 | 不能混同的事实 |
| --- | --- | --- |
| 本地已受理 | 意图及必要恢复数据已可靠保存 | 不等于服务器已经提交 |
| 乐观已投影 | 本地金币、装修、文字或照片已即时更新 | 不等于真实账本可由客户端决定 |
| 服务端已提交 | 权威交易与回执已提交 | 不应被 UI 应用失败推翻 |
| 接收内容已就绪 | 必需结果和可打开内容已准备 | 不等于接收方已经阅读/领取 |
| 已消费或已拒绝 | 用户已接收，或服务端明确否决 | 不能靠超时、页面卸载自行推断 |

发送方正常主链：本地同步校验 → 保存不可变意图/必要媒体恢复数据 → 乐观投影与即时反馈 → 结束页面交互 → 后台提交/重试 → 回执对账。

“不让用户等待”是移除可避免的等待，不是取消授权、可靠落盘、支付平台确认或服务端核验。初次启动、必须重新认证、价格无法读取、磁盘写入失败等情况应有明确恢复路径，不得假装成功。

### 3.2 失败处理必须分型

| 情况 | 必须行为 |
| --- | --- |
| 请求超时、断网、连接中断、暂时性服务错误 | 视为结果不确定；保留原意图，退避重试，不直接回滚已确认结果 |
| 服务端明确余额不足、配额耗尽、无权限、价格变化 | 结束该次授权意图，精确撤销它的乐观投影，说明原因；不得覆盖用户之后的新操作 |
| 服务器成功，但本地渲染/回执应用失败 | 重试本地应用；不能重新购买、重新发奖或显示服务端购买失败 |
| 本地保存意图失败 | 不展示“已可靠受理”；保留可恢复输入并提示重试 |
| 用户切账号/解绑后旧请求返回 | 用身份/关系版本丢弃不适用回执；不得污染新账号或新关系 |
| App 被关闭或进程被杀 | 下次按持久化意图恢复；不能依赖旧页面仍挂载才能完成 |

静默不等于隐藏永久失败。暂时错误可后台恢复；明确拒绝、需要重新授权或无法恢复的数据必须给一次清楚、可操作的说明，不能无限假成功。

## 4. 金币、购买、奖励：只有一个权威账本

### 4.1 身份和幂等合同

每个持久化操作至少能追溯：操作 ID、发起账号、作用对象、必要的关系版本、本地业务日期/时区、原始请求、幂等键和当前阶段。价格相关还需要商品永久 ID、报价/批准总额及目录版本。

- 重试重放同一个不可变请求，不能临时换商品、换账号、换价格或生成新幂等键。
- 同一键不同意图必须报冲突，不能“以后来参数为准”。
- “请求成功”与“本地应用成功”分开保存和处理；有回执时不再重发经济请求。
- 进程重启时，若本地回执尚未持久化，可用原请求向服务器幂等查询/重放；服务端必须保证不会再次收费或再次发奖。
- 监听器单独隔离异常。评分、日志、动画、React 更新不能影响已确认经济结果，也不能阻止其他监听器完成身份清理。
- 本地可用余额包含已有未确认支出的保留额；后台余额回包不能把这些保留额抹掉。

### 4.2 服务端结算合同

- 权威校验身份、商品状态/类型、价格、库存归属、Plus 权限、配额和余额。
- 同一结算中的扣款、库存、摆放和回执必须原子化；后面的商品拒绝不能留下前面商品已扣款的半套结果。
- 结算使用一致锁顺序，避免购买、赠送、接收礼物相互死锁。
- 已成功回执重放不能重新摆放旧商品，覆盖用户后来选择的装修。
- 已成功扣款不能因前端异常自动执行第二笔扣款或无依据退款；退款/补偿必须是明确、可追踪、幂等的经济操作。
- 同步发出的通知事件不得先于事务提交；事务内建立发件记录、提交后投递是一种可用实现，不能把未提交事实推给用户。

### 4.3 两类支付不能混淆

App 内金币消费可在可靠意图保存后即时投影；StoreKit / Play Billing 的真实订阅和现金购买必须尊重支付平台的确认状态。不能因为“乐观体验”提前把未购买成功的会员当成权威权益。

### 4.4 订阅与金币充值的状态及恢复隔离

- 共用一个商店连接和全局监听器，但“连接就绪”不等待历史收据核验或会员缓存刷新。订阅恢复和金币恢复分开执行，金币弹窗的待处理检查只等待金币订单。
- 仅正在进行的主动付款窗口保留跨商品防重入；历史订阅失败、账号归属冲突或会员刷新超时不能长期锁住独立金币充值。
- 用户取消是正常退出：释放本次 busy 状态，停留在原金币弹窗，不显示 `Purchase cancelled`、`Retry store` 或 `Check pending purchases`。界面由类型化状态驱动，不能解析英文文案来决定恢复行为。
- 未发起付款的失败、明确商店拒绝、等待批准、结果不确定和服务端已确认到账必须分开处理。付款请求发出后的未知异常不能直接推断未扣款；待确认订单保留安全恢复入口，不提前发币。
- 金币到账反馈以权威回执为界，不等待 Apple finish 或额外刷新；交易收尾失败保留成功事实，在 StoreKit 重放/前台恢复时用原凭据幂等处理，不能重开付款或重复加币。
- 后台订阅归属冲突不向无关页面补弹，也不能计为会员恢复成功。主动订阅的归属冲突仍给可操作说明，保留服务端账号校验；不得靠绕过校验来解决 Sandbox 测试冲突。
- 旧身份核验晚返回不能更新新账号会员/钱包或清除新操作状态。预检查缓存、订单回执和业务就绪状态不能混为一个全局成功/失败开关。

### 4.5 商店核验与支付收尾

- Apple 的历史有效签名仅为查询凭据，不代表当前仍有权益。必须使用官方库校验签名、App、环境和账号归属，再查官方当前订阅状态；过期、撤销、暂停、待支付或缺失有效到期时间不能新授予 Plus。Google 同样以官方当前购买状态为准。
- 客户端不能提交可信金币数、订阅 tier、购买环境或任意到期时间。产品 ID 绑定服务端商品表；商店凭据绑定原 App 账号，删除账号后保留不含用户内容的凭据占用记录，不能被别的账号重新认领。未绑定的旧收据缺少账号标记时不得“先到先得”。
- 支付平台明确失败、余额不足或待批准不能发币/授予会员；服务端临时不可用不等于未扣款。已扣款但核验暂未完成，保留原凭据重试/恢复；不再次发起扣款，不承诺自动银行卡退款。现金退款由商店官方流程处理。
- Google 金币入账与消费收尾任务在同一数据库事务内保存；consume/acknowledge 异常在有租约、幂等、退避的后台队列处理，不能把已到账改报购买失败。任务吞吐、积压和商店确认期限必须随规模监测；不能把 cron 存在等同于无限处理能力。
- 退款/撤销通知须验证来源，并回查当前官方状态；乱序结果不能覆盖更新状态。漏通知由后台复核修复，正常按钮打开不做商店联网核验。正常 JWT 本地签名校验有到期窗口，不可宣称退出后旧 JWT 在所有接口立即失效。
- Airwallex 已退出当前 App 支付能力；兼容旧 URL 只返回 410，不解析订单或修改支付记录。历史订单不清空。

### 4.6 自动测试经济域

- 不使用客户端测试开关或测试账号白名单授予经济权益。服务器确认 Sandbox 购买后，无真实付费记录的账号自动固定为 sandbox；真实付费账号不得自动转成测试账号，sandbox 账号以后也不能变成真实经济账号，需另用账号。
- 测试账号之间可正常测试 Plus、金币、奖励及赠礼；与 production 账号配对不共享测试 Plus、不互送付费商品/Surprise、不建立跨域付费游戏。免费社交与已有历史可读资格不因本轮隔离被删除。
- 新账号在尚未通过测试购买验证时默认按 production 处理，不能因其伙伴是测试账号而静默转换。测试币不进入真实经济域；原有隔离钱包/旧测试回执不回填真实余额。
- Profile 中的会员标签仅为展示投影；经济授权统一查询当前有效的自有/当前互相配对且同域的伙伴权益。旧标签、旧 Duo code 或历史配对不能单独获得权益。

### 4.7 固定经济日历（与 Memories 分开）

- 每日金币奖励、Affection、Adventure、任务及照片等经济配额使用账号固定的 IANA 时区。既有账号在迁移 272 固定当前有效资料时区；新账号在首次经济使用时固定当时的有效资料时区，无效值按 UTC。之后改设备/资料时区不改变经济边界、不补发次数；日界线按固定时区的自然日及夏令时计算。
- 客户端经济日期使用服务端 `localDate` / `economicTimezone`；不能自己用设备日期重新打开配额。经济日历表不可由用户直接写入或删除。重试仍使用原始日期和幂等键，跨日明确拒绝后按既定恢复规则处理。
- 资料时区仍可用于本地展示、Home 昼夜等；Memories 继续采用第 10.1 节的固定共同日历，不能把经济日历改动传播到日记换页规则。
- `X-Burrow-Economy: 1` 表明客户端已拆分日期用途。旧客户端的 bootstrap 仅将返回的资料时区投影为固定经济时区，兼容其每日判断，不修改真实资料；其部分当地展示会暂沿用经济时区，完整分离需新版 App。新客户端保持资料时区与经济时区分离，不新增点击联网或全局订阅。

## 5. 红点、通知、内容准备：先可用，再提醒

### 5.1 必须分开的四个概念

1. 业务事件：例如对方提交了完整 Game、发了 Love Note。
2. 未读/待领取：服务端维护的用户消费状态。
3. 展示就绪：本机是否已准备好当前内容版本和首屏必需资源。
4. 已阅读/已接收：用户实际完成指定动作后的回执。

获取数据、准备图片、渲染弹窗都不能自动等同于“已读”。为防加载而暂不展示红点，也不能清掉真实未读状态。

### 5.2 处理顺序

| 阶段 | 责任与出口条件 |
| --- | --- |
| 1. 发起与受理 | 发送方即时反馈，后台提交不可变意图 |
| 2. 服务端提交 | 权限、交易与内容记录完成；未完成的 Game 不具备通知资格 |
| 3. 服务端内容准备 | 必需计算、生成、媒体状态及可读接口满足展示合同 |
| 4. 投递复核 | 推送前再次检查当前业务状态、接收者及关系；过时通知不可照发 |
| 5. 客户端静默准备 | 接收数据更新信号，补齐当前版本数据、本地快照和首屏必需资源；不阻塞当前页面 |
| 6. 原子发布就绪 | 核对账号、关系、业务版本仍一致，再发布 ready 和可操作红点 |
| 7. 用户打开 | 使用已准备快照直接展示；读取/接收回执后台处理 |

新功能必须写明自己的“可打开合同”：需要哪些字段、结果、素材、权限和版本，而不是只写一个 `loaded=true`。

### 5.3 版本和作用域规则

- ready 至少绑定当前账号/关系作用域、通知目的地、内容业务版本。
- 同一版本准备请求 single-flight；失败保留未读，后台有界退避，不持续热轮询。
- 新内容版本到达时，只更新对应领域准备状态；旧版本 ready 不能给新版本背书。
- 钱包变化、无关时钟跳动不能使已准备的 Game/Journal 失效，更不能触发整份历史重新 stringify。
- 旧准备任务完成时必须检查身份、关系、版本及自身 generation。过期任务不能把新版本标为 ready。
- 可以保留已准备旧内容供正常历史浏览，但不能用它显示“新内容已可查看”的红点。
- 红点数字根据既定业务聚合，而不是根据网络消息次数或请求重试次数累加。
- 准备失败不制造一个点了没反应的按钮；页面本身保持可操作，恢复时再发布提醒。

### 5.4 Game、Affection 的特殊约定

- Game 只有发送方完成所有必填选择并有效提交后，接收方才获得相应邀请/待处理通知；仅创建或启动游戏不能触发 `Game from ...`。
- 不用“发送方页面已经导航到等待页”代替服务端提交事实；服务端应以完成状态和答案有效性核验。
- 推送队列里已有的任务也必须在真正投递前复核，不能只修新建通知入口。
- Affection 未 Receive 的同类型事件按当前业务合同聚合：一个类型一个弹窗，数量更新；Receive 后后续事件开启新一组。不能重复发一次就再排一个同类型弹窗。
- 当前有六种可发送 Affection，因此同一接收批次最多对应六个类型弹窗；聚合不等于删除事件或少记发送次数。

### 5.5 系统 Push 与 App 内红点的边界

服务端可以确认内容业务已就绪，但不能凭空知道一台离线手机已经把图片下载完成。现有链路不应被描述成“服务端已收到每台设备的本地缓存确认”。

App 内红点必须有本地准备门禁。系统 Push 的冷启动、离线、过期权限、解绑、内容被撤回等情况要单独验收：尽量用已保存内容和本地素材打开；无法安全展示时进入明确的恢复/失效状态，不显示空白、不泄露旧关系内容、不把按钮留成死按钮。不能承诺任何离线设备的任何历史 Push 都绝对秒开。

## 6. 功能隔离：不是单纯拆文件

正常依赖方向：页面/展示组件 → 领域公共控制器 → 领域状态/队列 → 统一传输 → 服务端领域命令/事务。

必须遵守：

- 跨功能通过公开接口、明确类型的事件或不可变快照通信，不直接操作对方私有状态。
- 事件必须能表达发起人、作用域、业务 ID 和版本；消费者应能幂等处理、忽略过期事件。不要增加一个所有页面都监听所有消息的全局事件总线。
- 一个公共入口负责购买、另一个负责礼物领取、另一个负责照片保存等明确职责；不能把“共享”实现成任何页面都能随意改整个全局对象。
- 同一数据只有一个权威源头；页面本地状态只负责编辑草稿、选中态和短暂呈现。
- 新增字段时同步更新 selector 依赖和版本计算，但只扩展真正消费它的页面。
- 身份/权限撤销、必要的持久化队列等基础设施可跨页面运行，但必须有清晰生命周期和边界。
- 展示玩偶的渲染器不应导入相机/照片编辑页面；轻量图片解析 Hook 和重型编辑功能分离。

目前并非仓库所有历史模块都已迁移为理想的小领域模块。后续改动应沿上述边界收敛，不能把本文写的目标误称为“全仓库已经完全解耦”。

## 7. 独立房间、库存与商品：已修复问题的核心合同

### 7.1 归属必须显式

| 资源 | 权威归属 |
| --- | --- |
| 个人装修、选中的 Plushie | 房间 owner；不能按较小用户 ID 或 shared room 兜底 |
| 金币、购买库存 | 对应账号；伴侣拥有不等于自己拥有 |
| 配对内容、社交访问权限 | 当前双方身份及关系版本 |
| 商品目录、不可变公共素材 | 可共享，但选择状态和私有照片不可混入 |
| 礼物 | 明确发送方与接收方；接收后仅按业务规则修改接收方库存/房间 |

明确允许的当前伴侣照片编辑等社交动作，要独立校验 actor、owner、当前关系和目标玩偶；不能由此扩大为“可以装修对方房间”或转移对方库存。

### 7.2 两个 Plushie 购买入口必须一致

主 Shop 与 Plushie Shop 共用 `enqueueBurrowPlushie` 及其底层个人房间结算路径。可以有不同页面展示，但价格校验、购买/已有判断、扣款、装备、回执、失败恢复不能分叉。

购买成功不应先装备、跳 Home，随后因本地观察者异常又弹“购买失败”并撤销；同一操作的完成语义必须贯通队列与 UI。

### 7.3 旧共享装修恢复与协议保护

- 保留历史证据，优先有效个人装修；缺失项只能从本人拥有/明确免费初始物品中恢复。
- 不确定的布局归档并使用默认摆放；不能补造库存、扣款记录或他人的归属。
- 当前个人房间能力使用 `personal-v2` 协议与 v2 持久化意图；不能把旧 shared v1 意图重新解释成新个人扣款请求。
- 新客户端不得因为 v2 服务暂不可用而偷偷退回旧共享写接口。
- 旧客户端继续原兼容协议；只有更新后的能力客户端才启用个人房间。服务端上线不等于旧 App 的所有行为自动改变。
- 个人购买回执不应无故因为解绑失效；关系相关动作必须因解绑失效。两种作用域不能混用。

商品使用永久 stable ID；业务代码不能依赖数组顺序、素材序号或 Metro 的临时数字资源 ID 表示库存。常规商品维护只更新和上新；不要重新加入已下架商品的摆放兼容来绕过新校验。

2026-10-26 用户明确批准的有限例外：删除 Retired Shop 中 28 个测试期柜子/壁纸商品的原图、独占缩略图及 Admin 预览，在身份账本逐项标记 `retiredArtRemoved`。永久 ID、下架状态与业务历史保留，不能重用 ID、重新上架或用当前商品/分类图标替代其历史图片；历史图片区域留空。其他商品缺图仍须拒绝生成，不能把这次许可泛化为删除所有退役商品素材。新客户端能力版本不再声明这 28 个 ID，旧客户端能力记录保留；新 App 发布前同步生成的 API 能力映射，不执行生产商品/账本清理。

## 8. 原生绘制与图片：防止“一页坏了，全 App 跟着坏”

### 8.1 Plushie 连锁显示异常的已确认机制

此前 `react-native-svg` 的 `ForeignObject` 包住原生 React Native View，快照路径修改了原生子视图的 hidden 状态。Fabric 回收复用后，普通卡片可能继承异常状态，表现为 Game/Surprise/Music 等无关页面内容消失。

这不是只加几层 React 组件或清一个 JS 列表就能彻底解决的问题。必须：

- 在当前项目的 SVG 蒙版内只使用 SVG 图元、路径和图片，不放 RN View/原生图片子树。
- 不重新引入 `ForeignObject`；普通容器、相机编辑器不能嵌进该快照通路。
- 蒙版沿用由实际透明区域生成的几何数据，不能用矩形底色遮到正常头发、服装、白色装饰或外部透明区。
- 升级 SVG/Fabric/图片依赖后重新做原生视图回收反例测试，不能因为版本号变了就自行撤销保护。
- Expo Fast Refresh 不保证修复已经被污染的原生视图池。拿到修复后需完全退出并重新打开 App；缓存清理不是根因修复的替代品。

### 8.2 图片解码与缓存规则

- 显式 `expo-image` 解码统一经过 `native-image-decoder.ts`，首次初始化合并；初始化成功后仍保留有界并行，不能把所有解码永久串行化。
- 该保护来自已观察的崩溃栈和原生共享管理器 lazy 初始化代码；它是有证据的缓解措施，不能描述成已证明 SDK 所有崩溃只有这一个原因。
- 初始化失败可重试，不永久缓存一个 rejected Promise。
- 公共图片准备缓存、私有照片缓存、素材注册各有职责，不再为每个页面建立另一套私有读取/解码体系。
- 缓存 key 包含内容版本；保留项、并发任务和解码尺寸有预算。不得把像素预算误写成同数值的 MiB 内存保证；多个保留项还可能使软预算暂时超出。
- 本地素材不能持久化 Metro 临时数字 ID；绑定永久商品 ID 和正式生成的素材映射。
- 预览、Home、Collection、交互玩偶和 Skia 使用一致的图片/裁剪语义，不各自推导头像位置。
- 同一素材的普通 URI 与已预解码 ImageRef 路径都要检查真实布局。已复现 iOS ImageRef 提前应用 source 时，矩形容器中的金币图与冷加载比例不同；金币弹窗对方形素材使用统一方形展示框修复，不修改全局缓存、不裁素材，也不借支付异常解释图片放大。

### 8.3 私有照片与损坏文件恢复

- 本地裁剪先可靠复制到受管私有目录，再允许页面结束；不能长期依赖相机临时缓存路径。
- 预览立即显示，上传/确认在后台进行；成功后采用已保存裁剪，不重复编码、复制或上传。
- 照片版本绑定 `id + updatedAt`，并受账号 epoch 约束；旧照片异步完成不能覆盖新版照片。
- SVG 图片没有原来 RN 图片的解码错误回调。私有文件应在共享缓存读取层做一次有界、可复用的有效性检查，而不是依赖每个渲染器的 onError。
- 损坏缓存只失效对应资源，重新获取使用新的文件 URI；坏下载不发布，不保留为可用缓存。
- 下载、校验、移动文件等异步步骤后再次检查身份；不能在切账号后把旧照片写回新账号缓存。
- 未上传照片的 Plushie 显示 Camera 提示；不触发挤压反馈或玩耍任务，只有添加照片入口可正常响应。

### 8.4 Biscuit / Pinky 静态素材与账号身份

- `biscuit` / `pinky` 是账号永久视觉身份，不是服装商品，不改变 stable ID、价格、库存、钱包、解锁或个人房间归属。Pinky 以已确认的 `#ef9ba3` 离线像素蒙版素材为准，不在每帧实时染色。
- 普通服装仅替换头部与含手部/露出褐毛的身体图；奶油下脸、肚皮、鼻子、脚底肉垫及衣服不染色。耳朵、尾巴沿用原共享层，领口遮挡已合入对应身体图，保持原角色比例和层级。Default 遵循已确认毛色范围。
- Onboarding 顺序为日期 → 角色选择 → 匹配；已知伙伴选择时只提供另一项。首次同色冲突由服务端配对事务分配，输入邀请码的已认证操作者优先；对方尚未定稿的选择改为另一项。双方已定稿后重新配对允许同色，不能重置永久身份。
- 既有旧关系按已记录的历史发起方分配 Biscuit、另一方 Pinky；这是用户明确批准的历史恢复例外，不能声称所有旧记录均能还原实际输入邀请码者。未配对旧账号首次定稿默认为 Biscuit。
- 选择意图可靠保存且同键重试；角色只由服务端定稿。远端变化先静默暂存，下次 Home 进入并准备完整套图后原子采用，不在用户当前操作中换色。伙伴房间按显式 owner 选素材；切账号不可继承前一账号的颜色缓存。
- Home 使用现有五层原生动画；Shop/Collection 用预合成静态缩略图，不为列表每张卡解码五层动画。准备缓存包含 outfit、variant 和素材版本，按现有预算复用；不得重新引入不安全 SVG 子树或每帧 JS 工作。

## 9. 账号、关系与持久化生命周期

### 9.1 三个传输检查点

发起操作时捕获身份上下文；获取 token 后、真正发送前核对；读取响应后、应用数据前再次核对。旧意图不能拿到新账号的 token 后继续发送。

新的能力客户端发送 actor 标识时，API 必须核对它与验证后的 JWT 主体一致。身份字段不是授权凭据，不能信任客户端任意传入的 `ownerId`。

### 9.2 持久化与清理

- 所有持久化 key 进入共享注册表，明确账号、关系、会话或公共生命周期；禁止页面自行写裸 MMKV key。
- 登录、退出、切账号、解绑、重新配对时，清理范围由资源归属决定；不能靠“一律清空所有缓存”掩盖越界。
- 私有缓存、准备注册、已解码私有资源和订阅必须正确撤销；公共不可变素材可复用。
- 异步任务检查 session epoch；关系任务还检查 pair version。取消监听并不能代替回包时的版本检查。
- 删除账号时按既定隐私规则清理关联私有档案；不可为了恢复装修永久保留不应保留的用户资料。

### 9.3 敏感操作、数据权限与上传

- 普通客户端不直接写钱包、账本、订阅、库存、经济域、经济日历或购买凭据；通过服务端认证、授权、限流和原子 RPC。RLS、列权限、Storage policy、RPC EXECUTE 权限都需检查，不能只依赖前端隐藏按钮。
- 删除账号要求在线确认用户及仍有效的会话。已绑定账号通过其已确认邮箱的短期、限次验证码确认；验证码不返回给客户端、不明文落库。匿名账号没有独立恢复凭据，保留明确两次确认及当前活跃会话检查，不伪称等同邮箱二次验证。
- 删除任一步失败不能报成功，保留可安全重试路径；Auth 删除后凭据 tombstone 不能因级联删除而变为可认领。私有媒体仍沿用既定延迟清理任务与归属检查。
- 头像经身份绑定上传票据、限流、体积/尺寸/格式检查及服务端真实解码、重新编码、去元数据后采用；禁止恢复 avatars 公共 INSERT。原有公开头像不因此变成私有，其他私有媒体仍按账号/关系隔离。
- 关键资金/删除接口的限流依赖不可用时应安全拒绝；日志不输出密钥、购买 token、验证码、私有内容或完整签名收据。密钥仅存服务端安全配置，不嵌入 App 或导出到交付文档。

- 页面 Done/OK/Back 必须能结束当前交互；网络完成不能重新导航到用户已经离开的页面。

### 10.1 Memories Room：双方保存完成、固定共同日历与分层已读

详细审核与实施说明见 [Memories Room 排查与改版方案](memories-room-review-and-plan.md)。用户批准后，具备 v2 能力的双人日记采用以下合同；旧客户端协议与未配对私有日记保留兼容边界。

- 双方各自明确 Save 并在服务端有效保存后完成一页，当天立即进入 History；未完成不换题，长时间离开不补造空白页。题库按完成序列循环，页码单调递增。
- “第二天”为固定共同日历时区的次日零点，不是 24 小时后，也不是双方各自的当地零点。采用现有较小 UUID 一方的日历时区并冻结到日记页/后续边界；这是日历规则，不是房间或库存归属规则。支持夏令时自然日计算，旅行或改 profile 时区不移动已有边界。
- 输入即保存本地草稿；仅按 Save 才进入受身份/关系保护的持久化提交队列。可靠受理后立即展示保存预览，后台退避重试；不把本地受理当成双方权威完成。相同不可变请求使用相同回执键，已提交旧回执不能覆盖后来的修订。
- 每作者一条最新答案，最多 1500 字符；预览四行尾部省略，全文不截断。本人可编辑当前/历史非空回答，不能编辑对方；历史编辑不重置完成时间或换页时间。编辑冲突保留草稿，拉取最新版本后由用户明确 Review/Save，不静默覆盖。
- 保存与草稿不拥有导航生命周期；编辑时不禁用返回手势，不等待网络，不把第一次 Back 仅解释成“退出编辑”。无返回栈有 Burrow 兜底，全文弹窗有独立关闭和 Android Back 出口。
- 伙伴答案修订和新页各有独立提醒版本；接收端完成必要内容准备后才发布红点。跨天未查看的答案仍在 History，点击 History 只消入口提醒，不把各页全已读；点击具体 Page 只确认实际显示的版本。全文/编辑覆盖期间不提前消费下层新修订。
- History 每屏约 4–5 条（小屏可更少），服务端稳定 UUID 游标每批 10 条。未读详情准备每批最多四页、并发二，分批让出 UI，不一次发起数百请求；准备失败保留真实未读。
- 未配对私有日记保持原来的本地日历规则；旧 partial/solo 历史不删除。v2 首次启用接续旧最近一页；旧客户端与新客户端在同一关系下读取同一 current page，旧日期分页仍可用。`X-Burrow-Journal: 2` 明确通知协议能力：只有新客户端接收新页/跨天历史元数据，旧版保留原通知形状，不让新元数据破坏旧版准备门禁。完整新界面与历史提醒需要新 App，API 上线不自动替换旧 App 界面。

### 10.2 Adventure v5：协作只共享进度，不共享奖励

- 新行程单人为 Free 6 小时、Plus 3 小时（2x），由服务端当前有效同域权益冻结。既有进行中行程保留原日期与结果；新行程中升级、过期或重复刷新不重新加速。旧客户端新开始也采用新时长，但旧协议不启用协作。
- 完成自己的 log 后提交 Start；若当前互相配对且同经济域的伙伴有可加入 v5 行程，继承其进度。仅将加入时的剩余时长除以 1.5，双方同一结束时间；例如剩余 11 分钟加入后约 7 分 20 秒结束。剩余 ≤600 秒不能加入，后启动者另开个人行程。
- 两人同时开始、重复回包和重启恢复仍由同一事务与幂等回执决定；有关系版本约束。v5 失败不能偷偷改投旧协议。旧持久化 v4 意图仍按原请求恢复，不能被解释成新协作请求。
- 每人必须有自己的 log、每日配额、Adventure 记录、遇友剧情、结果和宝箱；不能共享钱包、发奖结果或多拿次数。付费规则、经济时区和跨测试域隔离保持原合同。
- 单人 Free / 单人 Plus / 双人 Free / 双人 Plus 分别展示 Nudge / Nudge+Plus / Couple Mode / Plus+Couple Mode；单人 Plus 文案 2x、双人 Free 1.5x、双人 Plus 3x。Couple Mode 是状态显示，不是可点击开关。不可邀请时显示真实单人状态，不留下假可点按钮。
- Nudge 每队行程最多成功排队一次；本地可靠意图即反馈、后台重试同键，服务端事务出箱。真正投递时复核当前关系、有效行程、可加入窗口及接收方资格；过期、已加入或已另开不再发送。Push 仅投递到已声明 v5 能力的设备，不自动替对方写 log 或开始行程。
- 双头像用同一路径、同一 UI 线程进度与摆动相位；先启动者在前，后加入者跟随。领先头像初始不遮铲子；跟随头像起步允许遮铲子。伙伴加入只调整时间锚点与剩余速度，不重挂页面、不重播摆动、不让已显示进度倒退。
- 服务端通过私有 `bunny_changed` / `adventure_changed` 信号更新必要快照；不让角色或倒计时信号触发 Game、Surprise 等无关内容全量失效。原有结果就绪、内容准备与红点消费门禁保持不变。
- 能力通过 `X-Burrow-Bunny: 1` / `X-Burrow-Adventure: 5` 显式协商。迁移 273/274、API 与客户端分开发布；先具备兼容服务端，再启用新 App。新 v5 意图只有收到当前身份/关系匹配的服务端能力快照后才后台提交；旧 API 未声明支持时保留原意图重试，防止旧端把未知版本当 v1。视觉目录更新只追加对应客户端能力，不变更商品/活动目录或重抽已有预留结果。

### 10.3 Touch Note v2：触碰消息，不是赠送商品或刷任务

- 本节以用户在 2026-10-26 明确确认的 15 张 UI 及后续六点答复为准。自己 Plushie 默认保留 Squeeze / Bonk，右上方使用 `touch-note.webp`，三点菜单提供 Touch Note History；伙伴默认仅 Change Photo 与历史入口。录制、完成、预览、播放共用玩偶大小/位置和房间背景，不保留质量选择器或旧 Love Bomb 操作页。
- 首次进入提示 Start；以后有额度直接进入等待首次触碰页，无额度按实际 Free / Plus 显示升级或次日恢复提示。首次有效动作启动 UI 单调时钟，累计前台录满 60,000ms；App 内禁止返回、侧滑、Android Back 或移除本路由，不能手动暂停。系统进后台、锁屏或失焦时保存并暂停，回来重建锚点继续，不计后台时间、不退回初始页。身份失效、解绑、玩偶/照片撤销和根级安全流程优先，不锁整个 App。
- 每约 500ms 保存受管、加密本地检查点；正常系统中断即时保存，持有手指以 cancel 收尾。杀进程重开在相同身份/关系的入口恢复最近成功检查点，不增加 Home/公告/强更新的启动抢占。强杀、磁盘不足、系统挂起时不承诺零丢失；保存失败保留内存片段并明确提示。旧页面收尾必须检查捕获的账号、双方和关系版本。
- v2 首次有效按下计一次，同一连续持有期间每 500ms 再计一次，移动只采样轨迹，松手不另加；双指共用持有时钟，不翻倍。Squeeze / Bonk 成功按钮动作各一次，不以长按按钮重复刷数。普通互动每次反馈三个爱心，录制每计数一个；新增持有反馈不得生成额外任务、评分或奖励事实。v1 历史仍按原松手计数解码，不重写旧记录。最多双指、999 次、8,192 事件、完整 JSONB 256KiB；不存截图、照片字节或 Metro ID。
- 满 60 秒进入完成页，保留满进度爱心、总次数、Send Touch Note 和 Close and Leave；保存失败不得丢片段或自动重录。Close 弹确认，点外部留在完成页，Yes 明确丢弃后回默认页。Send 先可靠持久化不可变意图/幂等键，再反馈 Sending 并回默认页，不要求用户等网络，也不提前宣称发送成功。明确拒绝通知并保留可恢复记录；超时只重试原请求和原键，不静默换日期/换键。已提交成功不得被本地观察者或缓存异常反转为失败。
- Free 每账号每自然月一次，Plus 每账号每日一次，沿用固定经济日历、商店核验和同域共享权益。当天 Free 发过后升级 Plus 当天不补送，次日恢复；降级不恢复当月额度。仅服务端发送成功事务扣次数，录制、取消、接收、查看、播放、重播均不扣且不产生金币、库存、任务或奖励。
- Plus 按当前关系共用双方合计最近 10 条，包含双方发出/收到；每个消息只占一条，不再有 30 天 TTL。Free 每人只保留自己最新收到的一条，新收到覆盖旧收到（包括未读），不展示自己已发送的历史。失去 Plus 后按 Free 规则不可逆裁剪，升级不恢复删除项，历史页提前说明。发送/读取/推送资格复核均按当前权益裁剪，定时清理只处理超额记录。
- 消息保留发送者互动的玩偶目录快照；接收者即使未拥有，也仅可从消息入口看见，不增加库存或装修权限。照片走统一私有缓存与签名读取，仅当前关系的有效消息提供关联照片只读权限；删除照片不复活照片，轨迹和玩偶仍保留。
- ready、未读和已播放分开：素材/照片/轨迹准备完毕才亮 Burrow Partner’s Room 和伙伴房间 Plushie 红点；打开页面/历史不批量已读。接收者主动开始该条播放才保存 seen，发送者重播不消费接收者未读。Plus 历史双方可读，Free 自己发出的记录不可读。仍由 BurrowSyncGate 独占既有认证频道，触碰领域仅订阅当前身份的窄事件，不重拉无关页面、不关闭共享频道。
- 未读页点击信号爱心播放；Stop 冻结游标、形变、爱心和震动，Continue 从同一进度重建锚点；后台/失焦暂停，不在回前台自动补振。完成提供 Replay，从零重播。播放/暂停/结束页可返回伙伴 Plushie 默认页，之后从历史重播，不自动接着播下一条或恢复离开时的进度。
- 仅 Detailed / Standard 两档，默认本地能力允许时 Detailed；原生内存能力未知、可用预算不足、系统低内存或 Reduce Motion 使用 Standard。持续慢帧只从 Detailed 降 Standard，不重置进度、不自动升档；Standard 再遇内存警告暂停并说明，不退到 Light。静态等待预览不构成第三档回放。共用一套素材和既有形变/解码通路，不录逐帧视频；轻量原生模块只查本地内存/触觉能力，不含网络 SDK。内存数据是建议预算，不能保证 GPU/原生后续分配成功。
- 震动复用统一用户设置，最小间隔 140ms，高密度合并，迟到超过 180ms 不补振；持有轨迹按 500ms 节奏反馈。首次播放提供震动测试和明确的“我感受到了”确认，App 内关闭时由用户主动开启；系统明确关闭/硬件不支持时说明，未知系统开关不能伪称已开启。API 成功只代表请求被接受，不证明用户确实感到震动；iOS 系统总开关不可可靠读取，Android HAPTIC_FEEDBACK_ENABLED 仅为部分设置，不承诺所有硬件力度一致。固定六槽爱心，不为 999 次创建 999 视图/计时器。
- 解绑删除该关系内容、历史和待发 Push，并撤销私照消息读取；客户端关系失效清空草稿、准备引用和关系私有持久化。断网手机已接收的数据不能宣称被远程即时抹除。保留无手势/照片内容的额度、幂等摘要与回执防刷，新关系不继承旧内容。
- v2 需要迁移 277 → API v2 → 新原生客户端的兼容顺序；旧 v1 发送/回执和历史解码保留，旧客户端不获得其不能解码的 v2 消息/Push，新客户端在服务端未声明 v2 前不得发送 v2 片段。Push 能力按数据库消息版本筛选，不信任客户端伪造内容版本。2026-10-26 经用户后续明确授权，迁移 277 与 API v2 已按此顺序上线，既有数据/权限保护及新旧接口未登录鉴权检查通过；未发布 App，新增原生能力和完整 UI 仍需新版客户端。授权不扩大到其他功能、支付、钱包、房间归属或启动优先级。

## 11. 启动、强更、公告和弹窗互斥

优先级必须由统一启动/弹窗协调器管理，不能让 Home 各组件各弹自己的 Modal。

1. Splash/启动准备阶段检查最低支持版本。
2. 明确低于最低版本时只展示不可关闭的强更页，不进入 Home，不获取/消费公告。
3. 更新后重新启动，再按正常资格处理公告。
4. 公告在 Home 露出之前占住展示入口，Home 可以在下层准备；关闭后直接露出准备好的 Home。
5. 公告释放后，Daily Bonus 等后续弹窗再按既定资格进入，不能叠加透明遮罩。

具体规则：

- 强更按数值语义版本比较和平台匹配，不按字符串大小比较；Admin 更新最低支持版本原子替换，失败保留旧规则。
- 当前强更采用有界超时、无法确定时 fail-open：网络失败、版本不可解析或平台不匹配不能把所有用户锁死。若未来安全需求要求改变此策略，必须单独批准，而不是在普通修 Bug 中偷偷改成离线锁死。
- 新用户首次完成 onboarding 也检查公告入口；不能只在已有账号冷启动分支检查。
- onboarding 完成订阅后先 Connect Account；绑定/跳过后进入 Splash，不为了账号连接反复经历两次 Splash。
- 关闭 Onboarding Paywall / Connect 后，可靠保存本地设置意图；首次完成同步、登录 Splash、Home 数据/图片遮罩及首次公告查询共用最多 5 秒的视觉等待预算，不能逐段重新计时。网络失败/超时后进入已有缓存或打包默认素材的 Home；不伪造金币、库存、Plus 或已配对事实。后台保留原身份绑定的同步与重试，晚到结果不重复导航、不注入过期公告；本地保存失败、明确缺失身份仍保留恢复/登录出口，已明确强更不被兜底绕过。Home 的真实网络请求仍有独立硬截止，5 秒不是取消请求或经济事务的时限。
- 公告的已读资格按账号与公告 ID 管理，不能仅靠本机“本次显示过”。无截止日期不代表每次启动都重弹；有截止日期的过期未读公告也不应再展示。
- 公告按钮带有效链接则打开链接，无链接则关闭；关闭/标记阅读和身份检查保持一致。链接打不开要能恢复，不能把用户卡住。
- 启动请求都有截止时间，过期任务不能在用户已经进入其他页面后突然补弹。晚返回只能按现有策略准备缓存，不能抢夺展示权。
- Modal、手势锁、BackHandler、音频暂停/恢复、overlay reservation 均必须在退出时释放；透明但拦触摸的遮罩也是功能故障。

## 12. Paywall、会员和配置的单一来源

### 12.1 价格与试用

- 年/月总价来自 StoreKit 或 Play Billing 返回的商品/所选优惠，不是截图价格，也不是直接抓管理后台网页。
- Android 试用优惠的首期可能为 0；套餐总价展示与实际结算一致的后续周期价格，不能把 0 元试用当永久月费。
- 人均月费仅是展示估算：年费 ÷24、月费 ÷2；从原始数值计算后按币种精度格式化，不先把年费月均四舍五入后再除以 2。
- 卡片、按钮、试用标签和底部续费说明必须同步。同一截图里不同示例价格不能复制到正式页面。
- 只有确认存在且该用户符合资格的实际试用，才能显示 Free Trial；不能固定写 3 Days。
- 价格未就绪或读取失败时不能伪造价格、不能允许未知报价购买；保留重试。真实交易由既定支付层及服务端收据核验完成。
- Best Deal 需要对应可比较、同币种且确有优惠的价格事实。

### 12.2 规则、文案和素材

规则应有明确权威源和版本，客户端投影、API、SQL 与文案保持同一合同。当前仓库并不是所有规则都能在 Admin 动态配置；不能据此绕过发布或直接改数据库。

当前例子（只是 2026-10-25 的合同快照，修改前应核对现行实现）：

- Affection：Free 每天 1 次，Plus 每天 6 次；不能重新引入“Plus 无限次”文案。
- Adventure 新行程本地乐观时长：Free 6 小时、Plus 3 小时；协作仅将加入后的剩余时间除以 1.5，权威截止时间覆盖本地估算；旧进行中行程不改，不能使用旧的 1 分钟或 Plus 2 小时测试来约束新行程。
- 一个有效订阅按当前互相配对且同经济域的规则覆盖双方，不表示任意账号均能共享权益或资源所有权；测试权益不得流入真实账号。
- Plushie Touch：`packages/domain/src/plushie-touch.ts` 声明 v2 协议/事件/体积上限（保留 v1 解码兼容），API 和客户端共用，SQL 独立重复核验并做一致性测试。配额、固定经济日历和 Free/Plus 保留资格以服务端为准；客户端不能自报 Plus、次数或商品权限。调整这些合同需重新获批并同步迁移、测试和兼容说明。
- 商品维护入口为 `catalog/burrow-shop-products.json` 及正式生成流程，不在 Shop/Admin/奖励池各维护一份独立目录。

新增可变规则时，写清“谁是权威、如何版本化、谁消费、如何失效、旧客户端怎样处理”，而不是在页面里追加一个魔法数。

## 13. 常见故障：按机制排查，不按截图打补丁

| 现象 | 必查方向 | 不合格修复 |
| --- | --- | --- |
| 玩偶后多个无关页内容消失 | 数据是否真的缺失；原生 hidden/布局/回收状态；SVG 非安全子树；原生截图与点击能力 | 给每个页面加 force refresh、延迟、随机 key 或全量清缓存 |
| 头像变成其他图标 | 永久 ID 与临时资源 ID、素材映射、传入 source/URI、私有缓存作用域、原生视图复用 | 只换一张图片，不追踪错误 source 来源 |
| 购买后先成功再失败 | 服务端回执、幂等键、本地 confirm/observer 异常、投影撤销范围 | 再次扣款、把 committed 当 rejected、重置所有装修 |
| A 装修同步改了 B | 读写 owner、shared/低 ID 兜底、伴侣库存误用、协议与恢复逻辑 | 在 UI 隐藏对方装修，但保留共享写接口 |
| 红点点开仍加载 | ready 绑定版本、首屏资源、缓存作用域、点击是否重新强取网络 | 更早显示红点，或延长 loading 让它“等成功” |
| 通知到达时页面卡 | 全局快照订阅、重复预热、大数组扫描、解码并发、同步磁盘/状态更新 | 关掉通知、减少业务正确性校验 |
| 完成任务后 Claim 延迟 | 本地完成事实、投影与页面焦点刷新、是否只等远端 bootstrap | 用定时器延迟刷新或假造所有任务完成 |
| Done/Back 无效或连续操作卡住 | 遮罩/手势锁残留、重复提交锁、旧回调、异步导航竞争 | 再加一个全局 busy 锁 |
| 图片偶发不显示 | 本地文件存在不等于可解码；签名链接失效、版本与 URI 重用、身份切换 | 永久缓存失败结果或无限重试原坏 URI |
| 开发版问题重启才消失 | Fast Refresh 与原生生命周期差异、资源注册变化、回收池污染 | 宣称只在开发版所以无需修复或测试 Release |

每个 Bug 都要写出：触发条件 → 真实错误状态 → 跨功能传播路径 → 根因 → 约束修复 → 反例测试。临时绕过措施必须标明退出条件，不能成为无期限底层方案。

## 14. 新功能/修 Bug 的标准工作顺序

1. 先读本文、对应领域接口和相关现有测试；确认它是新需求还是恢复原合同。
2. 写影响面：读什么、写什么、订阅什么、是否碰到共享原生资源、哪些账号/关系/版本受影响。
3. 写正常、等待中、结果不确定、明确拒绝、账号切换、重启恢复的状态合同。
4. 优先构造当前失败反例。经济与权限问题使用真实领域函数/隔离数据库，不能只 mock 成成功。
5. 通过现有公共控制器实现，不复制另一条入口或另一套缓存。
6. 跑专项与跨功能回归、类型检查、架构边界检查；原生风险必须跑真实原生组件。
7. 有 UI 改动看真实截图和操作，不能只验证 JSX 文本/AX 节点存在。
8. 有性能影响做分场景测量，提交环境、样本数和剩余慢帧，不只报一个平均值。
9. 服务端/数据库改动按授权范围灰度、校验、发布与回滚；没有授权不改生产。
10. 更新领域说明、测试与本规范中受到影响的合同。交付时明确客户端是否已发布、哪些环境仍待验收。

### 14.1 每次改动的必填检查清单

- [ ] 该改动没有未经批准改变价格、奖励、配额、时长、通知资格或资源归属。
- [ ] 如调整既有约定，已有用户明确确认；对应章节、测试及变更记录已同步更新，交付包含新版文档链接；未获批准的部分保持不变。
- [ ] 用户主要点击不依赖网络往返；必要例外有明确状态和恢复出口。
- [ ] 本地意图可恢复；保存失败、超时、明确拒绝和 committed 后本地失败处理不同。
- [ ] 重复点击、重复回包、响应丢失和进程重启不会重复扣款/发奖/发送。
- [ ] 不会覆盖用户后续操作，不会用旧回执导航或关闭新弹窗。
- [ ] 对账号切换、解绑/重新配对、旧任务晚返回有作用域检查。
- [ ] 新订阅只包含必要字段；监听器/定时器/遮罩/后台任务会正确释放。
- [ ] 红点基于当前版本 ready；缺失必需内容不提前通知“可查看”。
- [ ] 没有裸存储 key、新的重复价格/库存源、临时资源 ID 持久化或 unsafe SVG。
- [ ] 两个同业务入口使用同一控制器；本人与伴侣、已有/未拥有/待确认状态均覆盖。
- [ ] 新功能之后，Home、Affection、Adventure、Game、Surprise、Music、Plushie/Collection/Shop 仍能正常打开和返回。
- [ ] 有反例测试及执行证据；失败用例没有通过删除断言或改成恒成功 mock 被掩盖。
- [ ] 不把 JS export、模拟器或单元测试通过说成 Android/iOS 真机、真实支付及全仓库测试全部通过。

## 15. 测试与发布门禁

### 15.1 当前可执行入口

在仓库根目录运行：

```bash
pnpm test:domain-isolation
pnpm --filter @novame/mobile exec tsc --noEmit
pnpm catalog:check
```

`test:domain-isolation` 包含当前领域回归与架构边界检查，现阶段也包括 Paywall/Onboarding。它不是所有历史/退役模块的全量测试；测试数量是证据快照，不是永远固定的产品指标。

个人房间数据库测试使用隔离 PGlite，不连接生产。CI 的准备方式见 `.github/workflows/domain-isolation.yml`。在独立临时目录准备依赖后执行：

```bash
BURROW_PGLITE_PATH=/绝对路径/node_modules/@electric-sql/pglite/dist/index.js \
  pnpm test:personal-rooms:db
```

需要导出时使用新的任务临时目录：

```bash
burrow_verify_dir=$(mktemp -d /private/tmp/burrow-verify.XXXXXX)
pnpm --filter @novame/mobile exec expo export --platform ios --output-dir "$burrow_verify_dir/ios"
pnpm --filter @novame/mobile exec expo export --platform android --output-dir "$burrow_verify_dir/android"
```

代码导出不等于原生构建、真实支付或设备验收。原生依赖变化另需重建二进制，Metro reload 不能补上新的原生模块。

现有边界检查能发现部分已知危险写法，但不是完整静态安全证明。未来新增替代导入方式、别名或渲染通道时，要扩展规则，不能绕过现有检测模式。

### 15.2 至少覆盖的故障矩阵

| 维度 | 必测情景 |
| --- | --- |
| 用户/关系 | A/B 独立、第三方拒绝、登录退出、切账号、解绑再配对、旧关系回包 |
| 会员/商品 | Free/Plus、免费/付费、本人已有/仅伴侣拥有、目录更新、报价变化 |
| 经济 | 余额充足/不足、重复点击、同键异参、提交后丢响应、回执应用失败、多商品后项失败 |
| 生命周期 | 页面退出、App 后台、杀进程、恢复队列、异步任务晚完成 |
| 网络 | 正常、断网、超时、临时服务失败、明确拒绝、恢复连接 |
| 磁盘/媒体 | 写入失败、文件不存在/损坏、上传失败、确认重试、版本替换、缓存失效 |
| 通知 | 未完成不通知、完整提交后通知、旧推送复核、新版本覆盖、准备失败、重复事件聚合 |
| 原生 UI | 玩偶蒙版反复挂载/卸载后其他卡片仍可见且能点；不能仅检查组件树有节点 |
| 性能 | 冷/热打开、连续返回和切 Tab、信息每隔数百毫秒更新时的操作、媒体预热并发 |
| 平台/显示 | iOS/Android、Release/开发版、小屏/大屏、安全区、大字体、长价格和非美元币种 |

测试用例更新必须先说明业务合同确实改变；过时的 1 分钟 Adventure、共享装修或固定美元价格期待应改成现行合同，不应为了旧测试重新破坏功能。

### 15.3 发布与回滚

- 先区分客户端、API、Admin、数据库、商品目录各自需要的交付；不要默认它们必须全部部署。
- 脏工作区只发布已审查的变更范围；核对候选源码/构建哈希及正式域名，不把其他任务的修改一起带上线。
- 迁移先在隔离数据库验证，保存必要的恢复证据、旧定义和权限；事务有锁等待/执行截止，失败保留旧规则。
- 数据保护不只看行数，还要检查金币、库存、订单、照片、账本、公告、强更等不应变化的数据和权限。
- 新协议先具备兼容服务端能力，再由有能力的新客户端启用。客户端金融意图不能在回滚时改投旧协议。
- 成功账本不是普通 UI 状态，不能用简单数据库回滚或清空队列抵消；补偿必须独立设计。
- 发布后做只读鉴权、版本、RPC 权限和域名校验；真实用户交易测试需要明确范围，不能擅自扣用户金币或触发付费。
- 不擅自发布公告、提高最低支持版本、强制旧用户更新或发布 App 商店版本。
