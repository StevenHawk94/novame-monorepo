## 0. 结论摘要（TL;DR）

| 问题 | 结论 |
|---|---|
| **要不要改成 Flutter？** | **不建议**。对你这个 App 的两个核心视觉需求，Flutter 都不是加分项：① 透明视频（HEVC with Alpha）—— Flutter 官方 `video_player` **至今不支持 alpha 通道**（多个 open issue 未解决），而 RN 侧 iOS 的 AVPlayer 原生支持 HEVC alpha；② Lottie —— 两边都成熟，打平。同时迁移会摧毁你现有架构最值钱的资产：`@novame/engine` 客户端/服务端**逐字共享**的 TypeScript 规则引擎。 |

## 1. RN vs Flutter：技术评估（对应你的问题 1 和最后的评估请求)

### 1.1 透明视频（HEVC with Alpha）—— 决定性因素

宠物系统是这个 App 的视觉核心：Home 页 3 秒循环的透明背景宠物视频、睡觉/清醒双状态、换装即换视频。这恰恰是 Flutter 的**已知短板**：

| | React Native（现状） | Flutter |
|---|---|---|
| iOS | ✅ `expo-video`/AVPlayer **原生支持** HEVC with Alpha（Apple 官方扩展），现有代码已在用且工作正常 | ❌ 官方 `video_player` 不支持 alpha 通道，[issue #155562](https://github.com/flutter/flutter/issues/155562)、[#120671](https://github.com/flutter/flutter/issues/120671)、[#127805](https://github.com/flutter/flutter/issues/127805) 均为长期 open 状态 |
| Android | ⚠️ ExoPlayer 不解码 alpha（[androidx/media #1388](https://github.com/androidx/media/issues/1388)），需要变通方案 | ⚠️ 同样问题，同样需要变通 |
| 变通方案 | Tencent VAP（side-by-side RGB+Alpha + shader 合成）有 RN 封装；或 expo-gl 自写 shader | [flutter_vap](https://github.com/redondoca/flutter_vap)（同为 VAP 方案）或自写 Texture + shader |

**关键结论**：
- **Android 的透明视频在两个框架下都是同一个平台级难题**（Android 系统本身不解码 alpha），解法也相同（VAP 格式：左右分屏 RGB+Alpha，GPU 合成）。换框架不解决这个问题。
- **iOS 上 RN 是"开箱即用"，Flutter 是"负分"**——你要放弃一个原生可用的能力，换一个需要引第三方库或自写平台层代码的方案。
- 建议（与框架无关）：双端统一走 **VAP 格式**（一份素材、两端一致、文件更小），iOS 也可保留 HEVC alpha 作为高质量路径。

### 1.2 Lottie —— 两边打平，略偏 RN

- `lottie-react-native` 包装的是 Airbnb 官方原生渲染器（lottie-ios / lottie-android），After Effects 特性覆盖最全；
- Flutter 的 `lottie` 包是 Dart 重实现，成熟可用，但个别 AE 特性支持滞后于原生库。
- 结论：**Lottie 不构成迁移理由**，甚至 RN 侧特性覆盖略优。

### 1.3 被迁移摧毁的核心资产：同构规则引擎

现有架构最值钱的设计是 `@novame/engine` + `@novame/domain`：**同一份 TypeScript 纯函数在移动端和 API 端逐字共享**（等级曲线、宝石规则、战斗数值、物品匹配、词典）。这是 v1 时代"客户端/服务端两套公式漂移"事故的架构级解药，CODEBASE.md 与代码注释中有完整决策记录。

迁到 Flutter（Dart）后只有两条路，都是净损失：
1. **把 engine 移植成 Dart 并双份维护** → 重新引入"两套公式漂移"风险，即 v1 踩过的坑；
2. **全部计算搬到服务端** → 每次展示派生值都要网络请求，损失首帧体验（现有 cache-first 架构依赖本地重算）。

缓解方案存在（TS 单一真源 + 代码生成 Dart + 双端契约测试），但这是纯增的工程成本，只为抵消迁移带来的伤害。

### 1.4 其他迁移成本清单

| 现有资产 | Flutter 下的命运 |
|---|---|
| 124 个 TS/TSX 文件的移动端 UI | 全部重写（Dart） |
| MMKV key 作用域注册表（为修复 P0-1 换账号数据泄漏事故而建） | 重新设计实现（Hive/shared_preferences + 自建作用域层） |
| expo-iap StoreKit 2 全链路（含服务端 JWS 验签联调） | 换 `in_app_purchase` 重新联调 |
| reanimated 4 动画、@gorhom/bottom-sheet、手势系统 | 全部重写 |
| 代码注释中沉淀的数十个已修复 bug（dual-React 崩溃、手势冲突、MMKV v4 持久化…） | 修复经验作废，新框架踩新坑 |
| apps/api、apps/admin、supabase、CI | ✅ 不受影响（框架无关） |

### 1.5 Flutter 真正能带来什么（公平陈述）

- 渲染一致性（自绘引擎，双端像素级一致）、Impeller 着色器预编译带来的动画稳定帧率、无桥接开销；
- 但你现在的栈是 **RN 新架构 + Hermes + reanimated 4（UI 线程动画）**，对这个 App 的动画密度（气泡、卡片、粒子、过渡）完全够用，现有代码也没有表现出性能瓶颈的迹象；
- Flutter 的优势场景是重度自绘 UI（复杂图表、画布编辑器、游戏化重渲染）。你的"游戏感"来自**视频 + Lottie + 插画**，恰好是 Flutter 相对最弱、RN 借原生能力最强的那一类。

### 1.6 评估结论

> **从 RN 迁到 Flutter 对 NovaMe 是错误的选择。**
> 理由排序：① 透明视频在 iOS 上从"原生支持"降级为"第三方变通"；② 同构规则引擎被摧毁；③ 3 个月以上纯迁移成本，用户价值为零；④ App 还是半成品，最大的风险是"迁移 + 补功能"双线作战导致两头失守。
>
> 唯一值得重新考虑的情形：你的长期团队只会 Dart / 已决定全线 Flutter 化 / 有 Web 端同构的硬需求。若是这些原因，请告诉我，方案会不同。

## 2. 若坚持迁移 Flutter：执行方案（对应你的问题 1）

> 即使我不推荐，你要求的方案如下，且这是把伤害降到最低的做法。

### 2.1 总原则

1. **后端、Admin、数据库、R2 全部不动**——它们与移动端框架无关，继续按 §5 的服务端工作流推进；
2. **不复刻现有半成品界面，直接按 PRD v2.0 建目标形态**（半成品里将被 PRD 改掉的部分绝不迁移）；
3. **规则引擎唯一真源保留在 TypeScript**（服务端继续用），Dart 侧只做「展示层重算」子集，用**共享 JSON fixture 契约测试**锁死双端一致（TS 测试与 Dart 测试跑同一组输入/期望输出文件）；
4. 透明视频双端统一 VAP 方案（见 §1.1），迁移期第一周就做技术验证 demo（宠物循环 + 换装过渡 + 睡眠切换），**这是整个迁移的第一风险项，必须最先证伪**。

### 2.2 阶段划分（约 22-30 周）

| 阶段 | 内容 | 时长 |
|---|---|---|
| F0 风险验证 | VAP 透明视频 demo（双端）、Lottie 性能样张、in_app_purchase 沙盒购买跑通、Supabase Auth（含 Apple/Google 登录）跑通 | 1-2 周 |
| F1 基础设施 | 项目脚手架（riverpod 或 bloc 状态管理、go_router、freezed）、存储作用域注册表重建（等价 MMKV 注册表）、ApiClient 移植、资产下载队列（P0/P1/P2 分级）移植、主题 token 从 ui-tokens 生成 Dart | 3-4 周 |
| F2 引擎子集移植 | level/gems/battle/item-matcher 展示子集 → Dart + 契约测试管线（CI 双跑） | 2 周 |
| F3 核心闭环 | 登录/onboarding/Home（宠物视频+气泡）/Reflect 全流程/Bags | 4-5 周 |
| F4 Kit 层与经济 | 5 个 Kit、Quests、皮肤/场景商店（服务端目录化，见 §5）、Me 页 | 4-5 周 |
| F5 社交与变现 | Friends 全套新功能、Widget（原生 Swift/Kotlin，两框架成本相同）、IAP 双平台、游客模式 | 4-6 周 |
| F6 收尾 | 安全复审、双端 beta、性能与崩溃率达标（崩溃率 <0.3%、冷启 <2.5s） | 2-3 周 |

### 2.3 迁移专属风险登记

| 风险 | 缓解 |
|---|---|
| VAP 素材管线要求美术重新导出所有宠物/皮肤视频 | F0 阶段确定素材规格并通知美术，与开发并行 |

| 迁移期间旧 RN 版本停止演进，线上问题只能双份修 | 冻结 RN 仓库仅接收 P0 修复 |

## 3. 先迁移还是先做完功能？（对应你的问题 2）

| 路线 | 工作量 | 结论 |
|---|---|---|
| A. 先在 RN 做完所有功能 → 再迁 Flutter | 所有 PRD 新功能**做两遍**（RN 一遍、Flutter 一遍） | ❌ 最差选项，直接排除 |
| B. 先迁 Flutter（复刻现状）→ 再做功能 | 复刻的半成品里有大量将被 PRD 改掉的部分（经济数值、排行榜删除、Quests 改版、Friends 重做），迁完即作废 | ⚠️ 次差 |
| C. 迁 Flutter 时直接按 PRD 目标形态重建 | 每个功能只做一遍，但仍承担 §1 全部迁移成本 | ✅ 若坚持 Flutter，唯一正确姿势（即 §2 方案） |
| **D. 不迁，RN 上直接实现 PRD** | 每个功能只做一遍，且复用全部现有资产 | ✅✅ **推荐**（即 §4 方案） |

**判断依据**：迁移决策的本质不是"先后"问题，而是"要不要付 3 个月纯成本"的问题。一旦决定付，就绝不该让任何功能被实现两遍——所以"先完成功能再迁"在任何情形下都不成立。

P1 经济系统 v2.0 对齐（引擎+DB+RPC+API）          ── 2 周
P2 服务端目录化（皮肤/场景/物件词典 Admin 可配）   ── 2 周

### 4.2 P1｜经济系统 v2.0 对齐（PRD §1、§8 ↔ 现有 engine/DB 的全部数值差异）

现状是「XP + 四叶草(clovers) + 宝石(gems)」三轨，PRD 收敛为「货币 + 8 维度分数」双轨。差异清单：

| 货币模型 | clovers = companion.xp − clovers_spent | 独立"货币"，上限 99999，所有行为发币 | engine 新增 currency 规则表；沿用 `xp_events` 账本模式（改名或加 `currency_events`） |
| Focus | +30 XP，1 次/天 | +30 币，**2 次/天** | 常量修改 |
| Reflect | +30 XP，3 次/天 | +30 币，3 次/天 | 一致 |
| Quiet Wins | +20，1/天 | +20，1/天 | 一致 |
| New Lens | +20，1/天 | +20，1/天 | 一致 |
| True North | +50，1/周 | **+100**，1/周 | 常量修改 |
| Tame Enemy | +20，全局 1/天 | **+30**；免费 1/天，**付费每怪 1/天共 8 次** | 常量 + 门控逻辑改造（RPC 层按 tier 分流） |
| Visit Master | +0 | **+50**，1/48h | 常量修改 |
| 每日 Quest | 5 clovers/任务 | **+30/天** | 常量修改 |

**实施要点（保持现有安全架构）**：所有新数值仍走 engine 纯函数 + SECURITY DEFINER RPC + advisory lock + 账本模式；本阶段产出一次性的 v2.1 迁移组（含 down 脚本），老用户数据按「XP 余额 → 货币余额」一次性 ETL。

### 4.3 P2｜服务端目录化（PRD §1 经济系统细则 + §12）

PRD 要求「Admin 上传图/视频/文案/价格 → R2 + DB → App 不发版更新」。现状皮肤/场景/词典全部硬编码在客户端包里。需要：

1. **DB**：`cosmetics_catalog`（类型/名称/价格/R2 URL/是否 Plus 专属/上架状态）、`item_sheets`（雪碧图 URL + 64 宫格 keyword→坐标映射）；
2. **Admin**：目录 CRUD 页 + R2 上传（复用现有 product-assets 的 R2 通道与校验模式：格式白名单、大小上限、manifest 更新）；
3. **API**：`/api/catalog`（公开只读，带版本号/ETag）；购买接口改为从目录读价格（**价格永远服务端权威**，沿用 book-payment 的原则）;
4. **App**：目录静默拉取（复用现有 asset-cache 分级下载 + 版本比对），皮肤视频「预缓存下一个即将解锁项」；
5. **物件词典**：`dictionary.json` 改为服务端下发 + 本地缓存，匹配逻辑不变（engine 纯函数），初始 10 张 8×8 雪碧图按 `keyword-编号` 定位。

## 6. 你可能忽略的点（对应你的问题 3：行业最优体验补充）

1. **推送通知（PRD 缺失但被隐含依赖）**：好友 Messages 未读、好友任务邀请红点、Widget 内容更新，没有远程推送都立不起来（现在只有本地提醒）。需要 APNs/FCM + 用户级推送偏好开关 + 静默推送驱动 Widget 刷新。
2. **UGC 合规是上架硬门槛**：共创回忆/好友可见回忆让用户内容流向他人，App Store Guideline 1.2 要求配齐举报、屏蔽、拉黑、开发者 24h 内响应机制。v1 有整套 reports/blocks 基建可复用，但要接到新功能上。
3. **隐私默认值**：好友可见回忆详情建议**默认关闭**（opt-in）。日记是 App 里最敏感的数据，「默认公开给好友」一旦出一个负面案例就是致命伤；PRD 未写默认值。
4. **时区与"每日"边界**：所有 1 次/天门控在跨时区旅行、手动改时间时的行为要统一定义（建议：服务端按用户注册时区或 profile 时区裁决，客户端只显示；防手动改时间刷奖励——现有 RPC 按服务器时间裁决的模式要坚持，PRD 的宠物睡眠时段用本地时间没问题，但**发币相关一律服务器时间**）。
5. **匿名→正式账号的数据合并冲突**：游客模式玩了两周再绑定一个已有账号，两边都有数据怎么合并？（建议：绑定时若目标账号非空，让用户二选一并明确提示，不做自动合并——自动合并的边界 bug 是数据事故重灾区。）
6. **订阅家庭/送礼合规**：「买双人份送好友」不能走 Apple 送礼（IAP 订阅不可送礼），现有 duo 的「服务端授权 + 邀请码」模式是合规正解，PRD 的 Friend Pack 继续沿用即可——但文案要避免出现"gift a subscription"字样（审核敏感），用"share access"。
7. **AI 内容安全**：情绪干预功能（针对负面 reflect）要有危机内容策略——检测到自伤等高危内容时不能只给"鸡汤"，行业标准做法是展示求助资源卡片（各地区热线），这既是伦理要求也是平台审核关注点。
8. **物件词典的多语言**：关键词匹配基于英文分词，中文用户写中文日记会匹配不到任何物件 → 词典需要每关键词多语言同义词组（现有 dictionary 结构已支持 synonyms，内容要补）。
9. **Widget 的节制刷新**：iOS WidgetKit 有严格的刷新预算，「好友一更新就刷新」做不到，要靠推送 + 时间线预算设计，预期管理上别承诺实时。
10. **崩溃与体验监控**：上线前接 Sentry（或同类），冷启动/卡顿/崩溃率有数字才能守住"最优体验"。
11. **可达性**：Dynamic Type（ui-tokens 已有 textStyle 半成品）、VoiceOver 标签、减弱动效开关（视频/粒子密集的 App 尤其需要 `prefers-reduced-motion` 响应）。
12. **iOS 无法程序化添加桌面 Widget**：设置里的「Add the widget」按钮在 iOS 上做不到一键添加，只能做成图文引导教程页（Android 12+ 可用 `requestPinAppWidget` 一键添加）。产品预期要按此降级。
13. **视频素材量要提前排产**：PRD 叠加后每只宠物的视频需求 = 幼年期 ×（自然+睡觉）+ 成年期 ×（自然+睡觉）× 每套皮肤（每套还含 2 图 + 2 视频）。3 只宠 × 6 款皮肤的完整矩阵是大几十条透明视频，美术产能大概率是关键路径，建议第一周就定素材规格（分辨率/时长/VAP 格式参数）并排期。

## 8. 安全设计（对应你的问题 4，贯穿所有阶段）

### 8.1 立刻修复（P0，与产品决策无关，本周就该做）

| # | 漏洞 | 修复 |
|---|---|---|
| 1 | `/api/support-ticket` GET/PATCH **完全无鉴权**——任何人可读全部工单（含用户邮箱）并改状态 | 加 `ADMIN_USER_IDS` 校验（与 orders 同款） |

| 3 | CORS `ALLOWED_ORIGINS` 含 `*` | 收紧为 Admin 域名 + 移动端无 Origin 放行 |

### 8.2 架构级原则（已有，必须在所有新功能中延续）

- 所有数值（货币/维度分/购买/奖励）**只能**由 SECURITY DEFINER RPC 在 advisory lock 下写入，客户端零直写（PRD「所有 table 除管理员不允许 read/edit/delete」的正确落地就是现状的「客户端仅 SELECT 自己的行 + 写全走 RPC」，比字面上的全禁读更可用且等价安全）；
- 每个发币点都要有 `(user, source, ref_id)` 幂等键防重放（泡泡 +5、每 2000 分战斗奖励这类新增点尤其要）；
- 价格、tier 权益、次数门控永远服务端裁决；客户端 flag 只是只读影子；
- 新增的每个 API 使用统一鉴权 wrapper（顺手解决 §CODEBASE 里 40 处复制粘贴的隐患——support-ticket 就是这么漏的）。

### 8.3 新功能的专项威胁建模

| 功能 | 威胁 | 对策 |
|---|---|---|
| 游客模式 | 设备 ID 伪造冒领他人影子账号；恢复购买劫持 | 影子账号绑定 IAP 原始交易 ID（appAccountToken）；合并账号需双向确认；设备 ID 只作索引不作凭证 |
| 陌生人搜索 | 用户枚举、骚扰 | 精确匹配查询 + 限流 + 需对方审核；搜索不返回任何列表 |
| 共创回忆 | 恶意内容投喂给好友；对 AI 的 prompt 注入 | 举报/拉黑链路；AI 输入严格作为 data（system/user 分离，已是 ai.js 现状）；输出过滤 |
| 好友权限 | 越权读私密回忆 | 权限过滤在 SQL/API 层，逐接口写权限测试用例 |
| Widget | 敏感内容出现在锁屏/桌面 | Widget 只显示 emoji 与物件图标，永不显示 reflect 文本（与 Friends 的 emoji 速览原则一致） |
| 泡泡奖励 | 脚本刷 +5 币 | 服务端生成当日泡泡清单（幂等），戳破提交带泡泡 ID，每 ID 一次 |
| 上传/分享图 | 不当图片 | 分享图纯客户端合成不落服务器；头像已有 SafeSearch，维持 |
