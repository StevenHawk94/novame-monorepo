# Memories Room 排查与改版方案

日期：2026-10-24 · 状态：方案已获用户确认并实施；验证/生产交付状态以文末实施记录及报告为准。

依据：用户提供图 1–3 与六条需求，随后确认实施、共同日历时区冻结及验证后迁移 268/API 上线。遵守开发基线；新客户端仍须随 App 发布，不能把服务端上线表述成旧 App 已换 UI。

## 1. 改版前真实规则（历史诊断，非 v2 合同）

| 项目 | 当前实现 |
| --- | --- |
| 题目 | 50 个固定题，按共同日历日期相对 2026-10-01 的偏移轮换，50 天循环；不是完成一题再取下一题 |
| 日期 | 配对时取双方 ID 较小一方 profile 的 timezone，未配对取本人时区；服务端权威。此处只是现状说明，不把 ID 排序用于房间归属 |
| 页面创建 | 读取 snapshot 时为当天创建一页；同关系版本同一天唯一，页码取当前关系已有最大值加一。无需双方写完，甚至无需有人写过 |
| History | 早于今天、至少有一条回答的页面；包含当前关系和本人的 solo 历史。倒序每批 10 条，取第 11 条判断更多；按日期游标 |
| 保存 | 每页每作者一条最新回答，编辑覆盖该回答。保留 createdAt/updatedAt，不保存每次编辑的服务端正文修订历史 |
| 草稿 | 每次输入同步写入受账号/关系作用域保护的本地草稿，最多保留 100 个 target；不是后台发送队列，不会自动把未按 Save 的字发给对方 |
| Save | 真实 page ID 下先做乐观呈现，但网络请求仍由页面管理；失败回到编辑态。临时页需要先等服务端解析真实 ID，读取/保存均有约 20 秒 deadline |
| 权限 | 服务端验证当前关系；只能写自己 authorId 的回答。本人历史 solo 页保持私有，不因配对变共享 |
| 红点 | attention 只读取 `local_date = snapshot.localDate` 的一页中对方的回答版本；客户端按回答 ID + updatedAt 本地记录 seen。没有明确的新页发布提醒，也没有历史页未读汇总 |
| 自动已读 | 页面 focused 时对 `snapshot.today.answers` 标记 seen，未区分现在实际显示 Today、History 还是某个历史详情 |
| UI | 正文点击进入自己的编辑，伴侣正文不能展开；没有定高省略卡、全文查看弹层或每屏 4–5 个主题的翻页式 History |

当前源码对应规则不等于本轮已经核对了生产数据库的在线定义；本轮未连接生产、未读取真实用户日记。

## 2. “卡死无法退出”的排查结论与证据边界

### 已确认

1. `usePageBackGesture((historyPage || view === 'today') && !editor && !saving)`：编辑、保存期间禁用侧滑，普通页面内的历史详情也禁用。
2. 左上角 Back 在 editor 存在时只 `setEditor(null)`，第一下不退出；第二下才导航。对保存中编辑框仍存在的临时页路径，也会先收起编辑框。
3. Save 的同步任务生命周期与页面耦合：临时页解析、保存和冲突读取可能等待网络；草稿虽已保存，用户仍受到 saving 状态影响。
4. 退出只调用 `router.back()`，未提供冷启动/通知直达、缺少可返回栈时的安全目的地。
5. 页面使用完整 `useBurrow()`，不是最小 journal selector；还订阅钱包。后台无关状态会带来不必要重绘。每个输入变化会读取、整理和写入整份本地草稿字典，也增加输入路径同步工作。

### 已执行的诊断

- `node --test tools/test-couple-journal.cjs`：现有 15 项通过。它们主要覆盖旧日历规则、草稿、权限和保存，不能作为新版验收。
- 用真实屏幕函数与现有 hooks 夹具注入返回计数、侧滑选项、悬而未决的保存请求：编辑时侧滑为 false；第一次 Back 未导航，第二次导航；保存时侧滑为 false，但页头 Back 仍可派发。
- 因此本轮**没有复现“所有退出方式都完全失效”的原生死锁**。以上是已证实的导航陷阱/性能风险，不冒充唯一根因。遮罩残留、原生 responder、特定设备键盘与选择菜单仍需带追踪的原生复现。

### 修复原则

- 页面退出不等网络，不用 saving 禁用整个页面的侧滑或返回；持久化草稿和发送队列承担安全责任。
- 编辑状态的明确退出动作保存本地草稿、收键盘并离开；如提供单独 Cancel，仅取消当前编辑呈现，不偷偷丢草稿或删除已保存答案。
- 全文弹层有可见关闭按钮、Android Back 和外部空白关闭；只关闭自身。History 详情返回列表、列表返回当前页、当前页返回来源，缺少来源时返回既有 Burrow 主入口。快速连续返回有单次导航保护。
- 异步回执只更新对应领域缓存，不再重新打开已关闭页面、设置已卸载 editor 或拦截返回。
- 原生复现时记录按下 → Back dispatch → beforeRemove/transitionEnd、焦点、editor/saving、overlay owner、键盘/选择态及任务 ID，不记录正文。

## 3. 新体验与数据模型

### 3.1 图 1：当前页/历史页

- 保留书本背景，固定顶部返回与 History。页码与题目由 page 实体决定，不再用设备日期自行拼新题。
- 本人空白回答框点击即进入多行编辑，自动换行；编辑器内部有有界高度及滚动。Save 校验非空，保持现有最多 1500 的输入/服务端长度合同，本轮不顺带扩大限额。
- 每次输入保存本地草稿，退出/后台时刷新必要尾部数据；草稿不算已提交、不给对方通知。高频写入应合并，但可靠退出落盘仍须保证，不能为流畅而丢最后几个字。
- Save 先可靠持久化“明确提交意图”及原文、page ID、owner/pair version、base revision、幂等键，再立即收起编辑、显示保存反馈和正文。后台核验、重试和对账；不显示等待服务器的 Saving 阻塞层。
- 尚无真实页身份时，保留受关系及前序页绑定的本地意图，后台解析权威 page ID；不能将昨日/旧关系草稿挪到新题。实际绑定动作发生在首次发出服务端命令前，之后请求不可变。
- 已保存正文卡片有稳定高度，按实际字体/可用高度计算行数，`numberOfLines` + 尾部省略；省略的是显示，不截断原文。本人卡片右上 Edit，伴侣无 Edit；点击已保存正文统一打开全文，不再误进编辑。
- 显示真实头像和名字，使用既有轻量头像解析。长名字、缺头像、未配对、小屏、大字体有兜底，不导入照片编辑器。

### 3.2 图 2：全文查看

- 展示作者、保存/更新时间与完整正文；日期从已保存时间格式化，不使用查看日期。
- 高度受安全区约束，长文在弹层内部滚动；有明确关闭，不依赖“用户能猜到点背景”。复制文字不吞掉关闭/返回。
- 从缓存立即打开。正文未就绪不显示可点击的假入口，也不能打开空白弹层后再请求核心正文。

### 3.3 图 3：History

- 列表只展示 Page 编号、主题及未读红点，不在列表复制全部答案。
- 按书本内部高度、字号和卡片最小可点击尺寸决定每屏数量，常见屏约 4–5 条；小屏/大字体可以更少，不能为固定数量裁内容。
- 右上下一页，非首页提供上一页，末页禁用下一页；不得只有“下一页”而无法回到上一批。空历史仍可打开，显示空态且可退出。
- 建议最新完成页优先，按稳定的页序游标取数；UI 页大小不强迫 API 重取。当前屏/下一屏的索引与详情按预算准备，禁止全历史一次下载/解码。
- 某个条目可点击前，对应详情所需题目、双方正文和作者信息已经准备；翻页同样先准备下一屏再放开按钮，旧列表始终可用，不弹阻塞 loading。
- 历史详情复用图 1 组件，不复制另一套编辑、缓存和已读逻辑。

## 4. 已确认的新换页生命周期（与旧规则不同）

`未完成当前页 → 双方均明确 Save 且服务端确认 → 完成并立即进入 History → 次日新页可用 → 一次性切换当前页`

必须具备：稳定 `pageId`、关系版本、页序、题目快照/题库版本、开始时间、双方回答修订、`completedAt`、`nextAvailableAt`、当前页指针。存储字段以最终迁移设计为准。

1. 一方未提交，跨多天也不换题；仅本地草稿或乐观 pending 不算服务端完成。
2. 第二方首次有效提交时，在同一事务内记录 completedAt 和 nextAvailableAt；重复回包/编辑不能再次完成或推迟换题。
3. 完成页立即出现在 History；当天主页面仍展示它，次日才进入新页，不出现完成后空白页。
4. **建议“第二天”采用现有服务端共同日历时区的下一个自然日零点，不是 24 小时后。** 每页固定用于结算的时区及 nextAvailableAt，后续修改手机时区/旅行不提前或延后已排定的新页。是否另外改成可配置 couple timezone 不在本轮默认范围。
5. **建议题目按完成页序推进**，不是继续按全局日期跳题；已有题目和历史主题固定，不因题库文案更新被追溯替换。50题用完后继续循环的既有行为可保留，需在方案确认时说明。
6. 连续离线数日后只产生下一页，不凭空补造多个空白完成页。冷启动/新版本准备时由服务端幂等激活，数据库保证同一关系只有一个当前页、页序唯一；不能两端各生成一页。
7. 用户正在读/编辑完成页时到达换页时间，不替换当前文本框；后台准备下一页，退出编辑或明确前往当前页时再展示新页。旧草稿一直绑定旧 page。
8. **建议已完成历史页仍允许作者编辑自己的非空答案**，不重开完成状态、不延后下一页；用修订号/CAS 防多设备覆盖，冲突保留两版供用户确认。编辑后是否再次提醒，建议按最新保存修订产生未读，已存在的未读合并而非弹窗堆积。

## 5. 红点：保持先准备后通知，但补全跨天和历史层级

不能只给原来“当天答案”数组加一个 History 红点。服务端未读、当地入口提醒消除和本机 ready 必须独立。

| 类型/入口 | 出现条件 | 清除条件 |
| --- | --- | --- |
| 当前页对方回答 | 对方的新保存修订已核验，当前账号可读，页面内容已准备 | 用户主动打开包含该修订的对应页；只清此次实际呈现修订 |
| 新 Page | 服务端已激活下一页，题目及首屏资源已准备 | 用户主动打开该新页，不以进入任意历史详情代替 |
| History 按钮 | 存在未查看历史回答，且相应列表/目标可打开 | 建议点击打开 History 后消除此批入口提醒；不把所有历史答案标已读 |
| History 条目 | 该页包含尚未打开的对方保存修订 | 点击该格子并实际展示对应页后清除；不必额外强迫展开全文 |

- 当前 Page 的未读回答随着页归档保留原 page/answer revision，第二天转到 History 提醒，不删除、不按新日期过滤掉。
- 点击 History 只消该入口提示，条目红点保留；返回后不能同一批提醒立刻重亮。新修订到达可再次激活入口。该“入口提醒”和“内容未读”拆分需确认，避免把用户的“点击后消失”错误实现成全量已读。
- 外层 Memories Room 提醒同样区分新页/回答入口提醒与未读事实；进入当前页不能误清 History 内容。已读按账号、关系、page、作者修订隔离，不能用未来时间戳一把抹掉晚到事件。
- History 展示过程中有新回答到达：不抢焦点、不自动翻页、不自动将未在本次点击快照中的修订标已读。若详情正显示，则更新在安全点应用，新修订是否消费由明确交互/当前实际展示版本决定，不能“focused 就全已读”。
- 服务端应持久化阅读位置/修订确认，多设备与重装不反复误报；客户端即时消点，回执静默幂等同步。已读写失败重试，不以服务器读回延迟让已消红点反复闪烁。
- attention 元数据给当前页、新页和未读历史 page ID/修订，不传所有正文；准备协调器精确预取必要页。仅准备最近10条无法证明一个更旧的未读页已可打开，需按目标 ID 准备，不扩大为全量读取。
- 解绑/换账号立即撤销旧关系准备资格，过期异步回包不能重新发布。沿用既有私有正文缓存政策，不因“秒开”偷偷把伴侣全文永久落普通磁盘缓存。

## 6. 防丢、重试和并发

- 草稿、提交意图、服务端最新答案、可见卡片四种状态分开。输入自动保存不是自动分享给伴侣；Save 才授权提交。
- 页面卸载/后台/进程重启不取消已可靠受理的提交。同意图同键重试；新版内容形成新意图，旧回执不覆盖新版编辑。
- 超时未知结果保持 pending 并后台恢复，不能回滚整个旧 snapshot 盖掉对方刚写的内容。明确拒绝只撤销自己的对应投影，草稿保留。
- 保存成功后的本地移除草稿、缓存监听器、动画异常不能改写权威成功；每个副作用隔离，待应用回执可重试。
- 同页多端编辑使用 revision/CAS，不能自动把旧稿重新基于新版本覆盖；用户确认冲突后才产生新授权意图。
- 现在只存每人一条最新正文，不等于有修订档案。本方案中的 History 指完整 Page，不默认增加用户可浏览的所有编辑版本；如需该功能应另行确认隐私、保存时长及删除规则。

## 7. 数据迁移、旧客户端与 solo 边界

- 保留全部既有题目、答案、Page 编号、私人 solo 历史和关系访问限制。不能因为新规则只归档双人完成页而删除旧的一人回答页。
- 旧历史标为 legacy，继续可读；当前关系现有未完成页在迁移时明确选定为 active，其余旧记录归档保留。不得静默重新编号所有旧 Page 或变更已答题目。
- 新协议/能力门禁及服务端持久化当前页是必要部分；旧客户端仍按日期推断页面，不能未经混合版本验证就直接切服务端规则。需要设计旧读取/写入的兼容响应或显式升级路径，不能让 v1/v2 并行生成两套题或跨页写入。
- 未配对目前允许私有日记。新“双人完成”逻辑不把 solo 草稿冒充双方完成；建议 solo 页继续私有读写且单独保持现有节奏，新配对开启新关系页。该 solo 产品边界应确认，不能无意取消现有功能或向新伴侣泄漏私有历史。
- 迁移涉及 API/SQL 与 App；用户已明确授权验证后执行迁移 268 并上线 API。只发布该范围，不发布公告/强更或 App 商店版本，实际状态见实施报告。

## 8. 性能与验收计划

- 屏幕仅订阅当前身份、关系权限、作者展示信息、journal 页面和相关红点版本；不订阅钱包、商品、装修和秒级时钟。完成/轮换由领域 store 管理。
- History 索引、详情准备、草稿/outbox、阅读确认各有公共接口与明确作用域；不得复制新的全局 bootstrap 或事件广播体系。
- 翻页使用稳定 page ID/游标；保留当前页，后台整理按预算让出 UI。全文渲染有界，不挂载所有历史的真实页面。
- 按开发基线复核点击反馈 ≤50ms 目标、60Hz帧预算约16.7ms、>50ms慢帧警戒和准备后页面进入指标，不能把“50ms一帧”叫60fps；记录样本、构建和剩余慢帧。

验收至少包括：

1. 正常输入/Save/编辑/全文；超长换行、尾部省略原文无损、1500长度、空白拒绝、表情和大字体。
2. 编辑、键盘、复制/选择、保存请求不返回、冲突、后台回来、连点Back、通知直达无返回栈、全文/History反复开关；iOS原生与Android返回都能退出。
3. 草稿未Save不通知；Save立即反馈、断网重试、杀进程恢复、同键重放、已提交后响应丢失、不重复完成/发事件。
4. A先写B未写跨多天不换题；B补写后当天完成、次日仅一页；午夜/夏令时/旅行/修改时区、双端同时激活。
5. 跨天未读迁移History；打开列表不全已读，点一页仅清该页；同页后续修订、正在看的页收到新内容、多设备阅读和重装。
6. 历史数0/1/4/5/6/10/11/大量页、同日legacy与solo混合、稳定游标无漏页、翻页不能跨主题编辑、目录和正文均准备后可点击。
7. 账号切换、解绑再配对、历史solo隐私、旧任务晚返回、混合版本，旧草稿绝不投到新关系。
8. Journal反例加入领域发布门禁；更新旧测试的日历换题期待，保留并扩充幂等/权限/草稿断言；原生跨页回归Home/Plushie/Shop/Game/Surprise，不能只验证节点存在。

## 9. 已获用户确认的方案要点

用户已确认以下解释，新协议按此实施；旧版情况仅保留为迁移/兼容说明：

- 第二天 = 现有共同日历时区的下一个自然日零点；未完成不换题，隔多天不补造空页。
- 题目按 Page 完成序列推进；历史可编辑本人非空内容但不改变完成/换页时间；更新正文按新修订提醒。
- 点击 History 消入口提示，不代表把列表全部已读；点击对应 Page 才清该条内容红点。
- 未配对私有日记保留、与新双人 Page 分离；旧单人回答历史不删除。
