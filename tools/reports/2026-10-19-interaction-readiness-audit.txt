根因与修改
1. 旧红点依据未读摘要，而详情在点击后才读取。现在未读意图与内容就绪分离：
   用户/伴侣/配对版本 + 业务内容版本 -> 后台准备共享缓存 -> 校验当前版本 -> 显示红点。
   不因预加载标记已读。失败保留未读意图、限速重试，不拖住其他通知通道。
2. 页面各自持有缓存、焦点刷新及旧响应回写，导致先空后有、旧响应覆盖新结果。
   Journal、Love Notes、Moments 和 Game Room 现在消费共享缓存并订阅变更；
   账号/配对变更、旧版本回执、保存与读取竞态受到隔离。
   Moments 不只比较首页事件列表，还比较通知版本；必要时分批读取未读记录。
3. 常用主页面沿用提前准备、保留实例。二级入口分批预求值模块，避免点击时集中解析；
   可选图片解码和刷新避开原生转场。相框使用已挂载但不可见的轻量弹窗。
   没有预先挂载所有摄像头、播放器或表单，以免触发权限、播放和额外副作用。
4. 游戏后答者不再以本地“提交中”作为进入结果页的条件。最后选择保留在原页，
   收到真实完整结果再进入结果页，不展示空白/占位分数，也不伪造对方答案。
   完整缓存结果直接打开，后台刷新不得覆盖已完成结果。Check/Play 通知入口要求正文就绪。
5. 新服务端提交 RPC 将旧的三个串行数据库调用合并到一次事务，提交回执携带完整结果。
   仍由服务端验证权限、配对代次和题目；对方未提交前答案继续封存。
   旧数据库缺少新函数时回落旧链路；权限错误、网络错误不作为回落条件。
   因为答案存在保密边界，不承诺断网时算出尚未获授权的对方分数。

通知入口逐项审核
- Game Room 邀请、待完成、待查看结果：共享 overview + session 正文准备；结果必须含真实 result。
- 系统 game_invite/game_ready 推送：接入 prepared entry；ready 推送要求完整结果。
- Memories Room / Couple Journal：当天问题与答案版本匹配；已显示答案才确认已读。
- Love Notes / Home 信封：共享正文缓存、完整未读队列；提醒关闭与阅读确认分开。
- Moments：业务完成后后台增量刷新；未读记录不在首屏时分批补齐，再显示对应红点。
- Friends Room：沿用本地可靠交互队列，拜访内容预先准备，不提前完成/领取。
- Adventure 到达：当前旅程奖励计划与首个结算图片提前准备；到达红点受就绪约束。
- Affection：inbox 为已有正文来源；显示数量不超过可用正文，首帧直接建立队列。
- 商品礼品：现有 bootstrap 礼品与商品目录匹配后计数，保留现有接收权限和领取流程。
- Quests：现有完成状态已含领取展示数据；复用本地领取隐藏/失败恢复，未新增详情下载器。
- Surprise：复用已有音频/图片 prepare -> preparedSurprise -> 播放链路，不重复创建预加载器。
- 菜单、商店、装扮等非通知入口：沿用主页面保留、可选工作让出转场及可靠业务队列。
  没有把所有购买、解锁、配对验证改成无授权的乐观成功。
